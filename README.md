# Remnawave Easy-Install (fork eGames)

Переписанный на **Go** установщик/менеджер [Remnawave](https://remna.st) — форк оригинального bash-скрипта [`remnawave-reverse-proxy`](https://github.com/eGamesAPI/remnawave-reverse-proxy) от eGames.

Идея проекта простая: тот же самый функционал (установка панели/ноды, управление сертификатами, IPv6, шаблоны для selfsteal-домена и т.д.), но в виде одного нативного бинарника на Go вместо ~7300 строк bash, разбросанных по десятку файлов.

> **Текущий статус: активная разработка.** Часть функциональности ещё не портирована (см. раздел [«Что реализовано, а что нет»](#что-реализовано-а-что-нет) ниже) — такие пункты меню явно помечены как `🚧 в разработке` / `🚧 Not implemented yet`, никаких скрытых заглушек.

## Почему Go, а не bash

Оригинальный скрипт — это один гигантский `install_remnawave.sh` (2300+ строк) плюс модули на ещё ~5000 строк bash. У такого подхода есть реальные проблемы:

- **Хрупкость.** Любая опечатка в `sed`/`awk`/`grep`-пайплайне ломает всё молча, без компиляции и без проверки типов.
- **Нечитаемость.** Логика вида `grep -B 20 "proxy_pass http://remnawave" nginx.conf | grep "server_name" | grep -v "server_name _" | awk '{print $2}' | sed 's/;//' | head -n 1` — сложно понять, ещё сложнее исправить.
- **Внешние зависимости.** Каждый чих — это вызов `curl`, `jq`, `openssl`, `dig`, `awk`... если утилита отсутствует или ведёт себя иначе на другом дистрибутиве — тихий отказ.
- **Ноль тестируемости.** Bash-функции с десятками глобальных переменных практически невозможно покрыть тестами.

Go даёт статическую типизацию, единый бинарник без внешних рантайм-зависимостей (кроме `docker`, `certbot`, `ufw` — тех инструментов, которые и должны оставаться внешними), нормальную обработку ошибок и юнит-тесты для критичной логики (генерация паролей, парсинг доменов, работа с сертификатами и т.д.).

## Что реализовано, а что нет

### ✅ Полностью портировано и работает

| Модуль | Оригинал (bash) | Пакет в Go | Что делает |
|---|---|---|---|
| Проверка ОС/root | `check_os`/`check_root` | `internal/oscheck` | Проверка версии Debian/Ubuntu и прав root |
| IPv6 | `src/modules/ipv6.sh` | `internal/ipv6` | Включение/отключение IPv6 в `sysctl` |
| API панели | `src/api/remnawave_api.sh` | `internal/api` | Полный клиент Remnawave API (регистрация, xray-ключи, config-профили, ноды, хосты, сквады, токены) |
| Добавление ноды | `src/modules/add_node.sh` | `internal/addnode` | Добавление ноды к существующей панели через API |
| Шаблоны selfsteal | `src/modules/selfsteal_templates.sh` | `internal/selfsteal` | Скачивание/распаковка/обфускация случайного HTML-шаблона для маскировки |
| Домен-утилиты | части `install_remnawave.sh` | `internal/domain` | Извлечение базового домена, проверка DNS/Cloudflare, проверка wildcard-сертификата |
| Сертификаты | `check_certificates`, `get_certificates`, `handle_certificates`, `check_cert_expiry`, `fix_letsencrypt_structure` + меню | `internal/certs` | Полный цикл: проверка существующих сертификатов, выпуск через `certbot` (Cloudflare DNS-01 / ACME HTTP-01 / Gcore DNS-01), обновление, cron для автопродления |
| Установка ноды (Nginx) | `src/nginx/install_node.sh` | `internal/nginxnode` | Установка отдельной ноды за Nginx |
| Установка только панели (Nginx) | `src/nginx/install_panel_node.sh`¹ | `internal/panelonly` | Установка панели без совмещённой ноды |
| Установка панели + ноды (Nginx) | `src/nginx/install_panel.sh`¹ | `internal/panelfull` | Полная установка на одном сервере: панель + совмещённая нода |
| Управление панелью/нодой | `src/modules/manage_panel.sh` | `internal/managepanel` | Старт/стоп/обновление, логи, `remnawave` CLI, временный доступ к панели на порту 8443 |
| Preflight-проверки | — (см. раздел про баги) | `internal/preflight` | Проверка `docker`/`docker compose`/`certbot` перед установкой |
| Генераторы | части `install_remnawave.sh` | `internal/genutil` | Логины, пароли, JWT-секреты |
| Локализация | `src/lang/en.sh`, `src/lang/ru.sh` | `internal/i18n` | Полный словарь EN/RU (~400 строк переводов) |
| Главное меню | `install_remnawave.sh` (диспетчер) | `internal/menu` | Навигация, редизайн под data-driven структуру |

¹ **Важно:** в оригинальном проекте имена этих двух файлов не совпадают с их содержимым — `install_panel_node.sh` реализует установку **только панели**, а `install_panel.sh` — установку **панели с совмещённой нодой**. Мы называем Go-пакеты по факту того, что они делают (`panelonly` / `panelfull`), а не копируем путаницу из оригинала.

### 🚧 Пока не реализовано (явно помечено в интерфейсе)

- **Caddy** — как альтернатива Nginx везде, где она есть в оригинале. Осознанное решение: проект сфокусирован на **Nginx-варианте**.
- **WARP Native** (`src/modules/warp.sh`) — вне текущего скоупа.
- **Custom extensions by legiz** — этот пункт меню вообще убран из форка (не является частью Remnawave как такового).
- `choose_reinstall_type` (переустановка) — заглушка.
- Backup/Restore — заглушка.
- Автообновление скрипта (`update_remnawave_reverse`) — заглушка.
- Удаление скрипта (`remove_script`) — заглушка.

Все заглушки в интерфейсе выводят `🚧 Not implemented yet in this Go port.` / `🚧 Пока не реализовано в Go-версии.` — никакого молчаливого "ничего не произошло".

## Поддерживаемые системы

- **Debian 11 и новее** (11 «bullseye», 12 «bookworm», 13 «trixie», включая все точечные релизы вроде 13.6.0, и будущие версии).
- **Ubuntu 22.04 LTS и новее** (22.04 «jammy», 24.04 «noble», 26.04 «resolute», и будущие релизы).

Проверка версии — по числовым `ID`/`VERSION_ID` из `/etc/os-release` (`internal/oscheck`), а не по жёстко зашитому списку кодовых имён — так что новые точечные и мажорные релизы поддерживаются автоматически, без необходимости патчить код при каждом новом релизе Debian/Ubuntu.

Требуется запуск от **root**.

### Внешние зависимости на сервере

Сам бинарник не тянет рантайм-зависимостей, но для реальной работы функциональности нужны:

- `docker` + плагин `docker compose`
- `certbot` (+ `certbot-dns-cloudflare`, при использовании метода Gcore — `certbot-dns-gcore` ставится автоматически через `pip`)
- `ufw`
- `nginx` (устанавливается внутри Docker, отдельно на хосте не нужен)

## Установка и запуск

Готовых бинарных релизов пока нет — собирайте из исходников (см. ниже). Планируется добавить `install.sh`/готовые релизы на этапе стабилизации.

## Сборка из исходников

Требуется Go **1.22+**.

```bash
git clone -b dev https://github.com/FlexEbat/Remnwave-Easy-Install.git
cd Remnwave-Easy-Install
go build -o remnawave-easy-install ./cmd/remnawave
sudo ./remnawave-easy-install
```

Проверка перед коммитом/PR:

```bash
go build ./...
go vet ./...
gofmt -l .   # не должно быть вывода
```

## Архитектура проекта

```
cmd/remnawave/          — точка входа (main.go): проверки ОС/root → главное меню
internal/
  ├── addnode/           — добавление ноды к панели
  ├── api/               — HTTP-клиент Remnawave API
  ├── certs/             — выпуск/обновление TLS-сертификатов (certbot)
  ├── domain/            — работа с доменами (extract/check/wildcard)
  ├── genutil/           — генераторы логинов/паролей/секретов
  ├── i18n/              — локализация (EN/RU)
  ├── ipv6/              — управление IPv6
  ├── managepanel/       — управление установленной панелью/нодой
  ├── menu/              — главное меню и диспетчеризация
  ├── nginxnode/         — установка отдельной ноды (Nginx)
  ├── oscheck/           — проверка версии ОС и прав root
  ├── panelfull/         — установка панели + совмещённой ноды (Nginx)
  ├── panelonly/         — установка только панели (Nginx)
  ├── preflight/         — проверки docker/certbot перед установкой
  ├── publicsuffix/      — Public Suffix List (вендор из golang.org/x/net)
  ├── selfsteal/         — шаблоны маскировочного сайта
  └── ui/                — цвета терминала, чтение ввода, очистка лога
```

Общий принцип: **один bash-файл/функция ≈ один Go-пакет/функция**, с комментарием над каждой функцией, указывающим номера строк оригинала. Это сделано намеренно — чтобы можно было в любой момент сверить Go-код с исходным bash построчно.

## Отличия от оригинального bash-скрипта

Мы не копировали bash 1:1 там, где это было бы явно хуже. Ключевые осознанные отличия:

- **Внешние утилиты → нативные библиотеки Go**, где это возможно и надёжнее:
  - `curl`+`jq` → `net/http`+`encoding/json` (пакет `api`)
  - `wget`+`unzip` → `net/http`+`archive/zip` в памяти, без временных файлов (пакет `selfsteal`)
  - `dig`/`curl ifconfig.me`/битовая арифметика для Cloudflare CIDR → `net.LookupIP`/`net/http`/`net.ParseCIDR` (пакет `domain`)
  - `openssl x509 -enddate` + `date -d` → `crypto/x509` напрямую (пакет `certs`) — единственное, что осталось на внешнем вызове — сам `certbot`, поскольку переизобретать ACME-протокол не имеет смысла.
  - `openssl rand -hex`/`/dev/urandom`+`tr`+`fold`+`shuf` → `crypto/rand` (пакеты `api`, `selfsteal`, `genutil`)
- **Числовая проверка версии ОС** вместо списка кодовых имён (см. [«Поддерживаемые системы»](#поддерживаемые-системы)) — не требует патчей при каждом новом релизе.
- **Данные словаря переводов сгенерированы напрямую из `src/lang/en.sh`/`ru.sh`** оригинального проекта — гарантия того, что тексты не разошлись при переносе, вместо ручного перепечатывания ~400 строк.
- **Правильные имена пакетов** `panelonly`/`panelfull` вместо копирования путаницы оригинальных `install_panel_node.sh`/`install_panel.sh` (см. сноску в таблице выше).
- **`targetDir` — параметр, а не хардкод.** В оригинале `handle_certificates()` жёстко использует `/opt/remnawave` для всех вызовов, включая установку отдельной ноды (которая физически находится в `/opt/remnanode`) — реальный баг оригинала. В Go-версии путь передаётся явно.
- **Реальный результат вместо мёртвого fallback-кода.** Из-за передачи переменной по значению (а не по ссылке) в bash-функцию `handle_certificates`, оригинальный скрипт никогда не получал обратно выбранный метод сертификата и использовал отдельную (избыточную) проверку файла на диске. В Go-версии функция возвращает реально использованный метод.
- **Данные-структуры вместо повторяющихся блоков `case`.** Главное меню — это `[]menuItem`, а не десяток скопипасченных `echo`+`case` веток.

Подробные построчные комментарии о происхождении и обоснование каждого отличия — прямо в комментариях к соответствующим Go-функциям.

## Найденные и исправленные баги

Помимо архитектурных отличий (см. выше), в процессе разработки и по фидбэку были найдены и устранены следующие проблемы:

- **`ExtractDomain` не понимал составные TLD** (`co.uk`, `com.au`, `co.jp` и т.п.) — для `sub.example.co.uk` возвращал `co.uk` вместо `example.co.uk` (наследие оригинального `awk`-однострочника, бравшего последние два лейбла домена). Исправлено: завендорили `golang.org/x/net/publicsuffix` (`internal/publicsuffix`, только stdlib-зависимости) и используем настоящий алгоритм Public Suffix List через `EffectiveTLDPlusOne()`.
- **Обрезанные сообщения об ошибках `CONFIG_NOT_FOUND`/`NGINX_CONF_NOT_FOUND`** — в оригинале эти строки ссылались на `$dir` внутри *двойных* кавычек bash-массива, который разворачивается в момент загрузки словаря переводов (когда `$dir` ещё не определена) — итоговое сообщение обрывалось на «...not found in » без самого пути. Исправлено: обе строки теперь используют `%s`, вызывающий код передаёт реальный каталог.
- **Отсутствовала preflight-проверка `docker`/`docker compose`/`certbot` перед установкой.** Раньше отсутствие Docker обнаруживалось только спустя ~5 минут ретраев в виде невнятного таймаута «containers not ready». Добавлен пакет `internal/preflight` (`CheckDocker` — проверяет не только наличие бинарника, но и что демон отвечает через `docker info`, и что плагин `compose` установлен; `CheckCertbot`) — подключён в начало всех трёх install-флоу (`nginxnode`, `panelonly`, `panelfull`), до первого вопроса пользователю.
- **Недетерминированный порядок вывода в «Update current certificates»** — из-за итерации по Go `map` (у которой нет гарантированного порядка обхода) результаты обновления сертификатов печатались в случайном порядке между запусками. Исправлено: домены сортируются перед обработкой и перед финальным выводом.
- **Хрупкий парсинг `nginx.conf` в `managepanel`** (временный доступ к панели на порту 8443) — поиск границ `server{}`-блока полагался на литеральные строки `"server {"` и `"\n}"` с нулевым отступом; при отличающемся стиле форматирования (табы, другое число пробелов, отступ у закрывающей скобки) поиск либо не находил нужный блок, либо мог случайно задеть чужой. Исправлено: написан парсер границ блока с учётом вложенности фигурных скобок (`internal/managepanel/nginxconf.go`), корректно работающий независимо от форматирования и вложенных `location{}`/`if{}`-блоков.

## Известные ограничения

- Caddy и WARP не реализованы (см. выше) — это осознанный выбор скоупа, а не забытая работа.
- Готовых release-бинарников/инсталлятора одной командой пока нет — только сборка из исходников.
- **Ничего не проверялось на реальной инфраструктуре.** Все тесты — юнит-тесты на чистую логику (парсинг, генерация, шаблоны, границы nginx-блоков) и smoke-тесты навигации меню с фейковыми серверами вместо реальных. Реальный `docker compose up`, реальный `certbot certonly` с настоящим доменом, реальный `ufw` — ни разу не прогонялись живьём в процессе разработки (в среде разработки нет Docker/публичного домена/доступа к нужным внешним сервисам). Это не значит «не работает» — код собирается, проходит `go vet`, и вся автономная логика покрыта тестами — но первый прогон стоит делать на тестовом сервере, а не сразу в проде.

## Разработка и вклад в проект

Проект развивается через build-in-public итерации: каждое изменение фиксируется бампом версии (`internal/menu/version.go`). Если хотите помочь:

1. Проверяйте `go build ./...`, `go vet ./...`, `gofmt -l .` перед PR — вывод должен быть пустым (кроме `go build`, конечно).
2. Портируя очередной bash-модуль — сохраняйте комментарии с номерами строк оригинала, это упрощает ревью.
3. Для тестов, не требующих реальной сети/Docker/certbot, предпочитайте юнит-тесты на чистую логику (парсинг, генерация, шаблоны) — так тестировались, например, `certs`, `domain`, `genutil`, `selfsteal`, `panelonly`/`panelfull` в процессе разработки.
