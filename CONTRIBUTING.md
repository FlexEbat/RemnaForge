# Contributing

## Стиль текста в проекте

Правила ниже применяются к коммитам, комментариям в коде и документации. Текст должен читаться быстро и не тратить время читателя на слова без информации.

### Активный залог

Пишите подлежащее-действие-объект. Не прячьте исполнителя действия за пассивной конструкцией.

- Плохо: «Ошибка обрабатывается функцией `CheckOS`»
- Хорошо: «`CheckOS` обрабатывает ошибку»

### Конкретика вместо общих фраз

Называйте файл, функцию, номер строки, конкретное значение. Не пишите «в некоторых случаях», «определённым образом», «соответствующая логика»: пишите, в каких случаях, каким образом, какая именно логика.

- Плохо: «В некоторых случаях функция может завершиться с ошибкой»
- Хорошо: «Функция возвращает ошибку, если `docker info` завершается с ненулевым кодом»

### Без вводных оборотов

Не начинайте предложение с «Стоит отметить, что...», «Важно понимать, что...», «Как известно...», «Отметим, что...», «Следует сказать...». Это слова-заполнители: удалите их, и смысл предложения не изменится.

- Плохо: «Стоит отметить, что эта функция не потокобезопасна»
- Хорошо: «Функция не потокобезопасна»

### Без длинного тире

Не используйте «—» и его ASCII-заменитель « - » как способ склеить два предложения в одно. Делите на отдельные предложения, используйте двоеточие, если второе предложение раскрывает первое, или запятую с союзом.

- Плохо: «Функция ничего не возвращает — она пишет результат в файл»
- Хорошо: «Функция пишет результат в файл и ничего не возвращает»

### Без наречий-усилителей

Слова «очень», «просто», «весьма», «крайне», «довольно», «действительно», «полностью» (когда не о буквальной полноте), «просто-напросто» не добавляют информации. Уберите их и проверьте, изменился ли смысл: в большинстве случаев не меняется.

- Плохо: «Эта проверка очень важна для безопасности»
- Хорошо: «Проверка блокирует запуск без прав root»

### Комментарий объясняет причину, а не соседнюю строку

Комментарий должен отвечать на вопрос «почему код написан так», а не пересказывать то, что и так видно из кода.

- Плохо: `// increment counter by one` над `counter++`
- Хорошо: `// certbot returns 0 even when it skips an unchanged cert, so track the file mtime instead` над кодом, который сверяет `mtime`

### Без закомментированного кода

Удаляйте код, который не нужен. Git хранит историю: закомментированный блок кода не документирует ничего, что не хранит `git log`, и превращается в мусор при следующем чтении файла.

## Язык

Код, комментарии в коде, сообщения коммитов, сообщения об ошибках, которые видит только консоль (`fmt.Errorf`, `log`), — по-английски. Тексты интерфейса и валидации, которые видит пользователь через `i18n.T(...)` (обе локали, `en` и `ru`), содержат перевод на оба языка — это отдельный контракт, раздел 4 `TECH.md`, не про язык прозы этого файла.

`README.md` (английский) — основная версия, источник истины по содержанию. `README.ru.md`, `README.zh.md`, `README.fa.md` — переводы с идентичной структурой (те же разделы в том же порядке, тот же переключатель языков первой строкой). Правка одной версии, меняющая факт (не опечатку), обязана попасть во все четыре в одном и том же коммите — разъехавшиеся версии хуже отсутствия перевода. `TECH.md` и `CONTRIBUTING.md` — только на русском, это внутренние документы для того, кто ведёт разработку, не для конечного пользователя.

## Формат сообщений коммитов

Заголовок коммита: `type(scope): summary`.

- `type` — тип изменения: `feat` (новая функциональность), `fix` (исправление бага), `docs` (документация), `refactor` (изменение кода без изменения поведения), `test` (тесты), `chore` (зависимости, CI, рутинные задачи не в коде проекта).
- `scope` — один пакет или одна область, которую коснулось изменение: имя папки внутри `internal/` без пути (`certs`, `menu`, `i18n`), либо `docs` для правок README/TECH.md/CONTRIBUTING.md. Если изменение затрагивает два пакета не по касательной, а как две отдельные причины, — это два коммита, не один с `scope` через запятую.
- `summary` — глагол в повелительном наклонении, строчными буквами, без точки в конце, **до 50 символов**. Отвечает на вопрос «что делает этот коммит», не «что было сделано». Не влезает в 50 символов с одним глаголом — значит коммит делает больше одной вещи, дели на несколько коммитов, а не сокращай слова до нечитаемости.

Примеры: `feat(notes): add archive filter to list page`, `test(validate): cover empty title case`.

Примеры на масштабе этого проекта: `fix(uninstall): report docker compose failure`, `feat(caddypanelfull): add node install flow`, `docs(readme): add xray reading list`.

Тело коммита (после пустой строки за заголовком) объясняет **только почему**, не что: что было сделано, уже написано в самом diff'е и в заголовке, пересказывать это в теле — трата времени читателя. Тело обязательно, если решение неочевидно из diff'а (например, почему выбран этот подход, а не другой, какая ошибка на самом деле воспроизводилась); необязательно для механических правок вроде опечатки.

Коммитить по ходу работы маленькими шагами: одна причина для изменения — один коммит, сразу после того как эта причина закрыта, а не всё разом одним коммитом в конце сессии. Каждый коммит должен проходить `go build ./...` сам по себе, не только финальный.

## Перед коммитом

```bash
go build ./...
go vet ./...
gofmt -l .   # пустой вывод
```

## Исправление багов

Если баг найден, чините его в той же единице работы, где нашли, независимо от размера или давности. Отдельным комментарием `BUG FIX:` объясните, что было не так и что изменилось. Совпадение с более старой версией кода не аргумент за сохранение дефекта.
